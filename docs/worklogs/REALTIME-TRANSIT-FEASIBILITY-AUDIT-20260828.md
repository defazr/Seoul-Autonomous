## A. 감사 목적과 잠금 충돌

이번 라운드는 실시간 기능을 구현하는 단계가 **아니다.** 다음 잠금을 **열 가치가 있는지 판단**한다.

| 잠금 | 출처 | 이번 조사와의 관계 |
|---|---|---|
| 실시간 데이터처럼 보이는 표현 금지 | `CLAUDE.md` 절대 금지선 ③ | 표현 규칙 — GO여도 문구는 별도 승인 |
| API 직접 호출 코드 금지(v1) | `CLAUDE.md` 절대 금지선 ④ | 구현 금지 — 해제는 별도 결정 |
| STATIC-FIRST / 외부 상태 도입 금지 | Phase 0 계약 | **해제 trigger 첫 번째가 "실시간 API"** — 조사 방향과 충돌하지 않음 |

**본 감사의 CONDITIONAL 판정은 잠금을 해제하지 않는다.** 후속 순서는 다음과 같다.

```
RT-1 연구용 실호출 검증  →  최종 feasibility 판정  →  (필요할 때) v1 잠금 해제 결정
                         →  아키텍처 설계  →  구현 승인
```

**RT-1은 잠금 해제를 전제하지 않는다.** RT-1의 API 호출은 제품에 외부 상태를 도입하는 것이 아니라
**API를 제품 밖에서 검증하는 감사**이므로, STATIC-FIRST·API 직접 호출 코드 금지(v1) 계약을
열 필요가 없다. 잠금 해제는 RT-1 결과로 최종 feasibility가 확정된 뒤 별도로 판단한다.

동대문·서대문A01(BIT 실시간 도착시간 명시)과 **같은 등급으로 집계하지 않는다.**
A741은 서울 버스정보 체계에 편입돼 있다는 **부분 근거**로만 분류한다.

### D-3. Gate 0 판정 = **POSSIBLE** (NO-GO 아님)

우리 자율주행 노선이 서울시 버스정보 체계(BIT·서울버스정보·포털 연계)에 **편입되어 실시간
도착정보가 제공된다는 공식 진술이 복수 노선·복수 연도에 걸쳐 존재**한다
(2024-11 A160 · 2025-10 동대문/서대문A01 = 실시간 도착 명시 / 2026-03 A741 = 체계 편입 정황).
정책적 패턴으로서 일관되며, 신설 노선이 버스정보 체계에 편입되는 관행이 유지되는 것으로 보인다.

**단, 다음을 증거로 승격하지 않는다:**

1. **카카오맵 11/11 등재는 단서일 뿐이다.** `routes.json`의 11개 노선이 전부
   `verificationLevel: kakao_seoul_verified`이지만, 이는 지도 서비스에 노선이 존재한다는
   뜻이며 **공개 API의 실시간 coverage 증거가 아니다.** 공식 출처 근거(D-1)와 분리해 다룬다.
2. **BIT 표출 ≠ 공개 API 포함.** BIT·네이버·카카오는 서울시와의 직접 연계로 데이터를 받을 수
   있으며, 그것이 곧 OA-1091/OA-1093 공개 API의 응답에 해당 노선이 포함된다는 보장은 아니다.
   **이 한 칸이 문서만으로 메워지지 않는다** → J절 DOCUMENT-ONLY LIMIT.

## E. Stop ID matching

현재 사이트 Stop identity: **ARS 5자리 stopId** (Graph 고유 267 / Stage 1 라이브 7).

**⚠️ 정정 (2026-08-28, 공식 개발가이드 확인 후)**: 초안은 "OA-1091이 arsId를 직접 지원"이라고
기술했으나, 공식 개발가이드(S5 `api.bus.go.kr` → 개발가이드 → Open-API 제공 목록)를 확인한 결과
**서비스별로 키가 다르다.**

| 서비스 | 대표 API | 요청 파라미터 |
|---|---|---|
| **정류소정보조회** | 고유번호별정류소항목조회 | **`?arsId=정류소번호`** — 설명상 "해당 정류소에 대한 접근 버스 **도착예정 정보**를 출력" |
| **정류소정보조회** | 정류소별경유노선목록조회 | **`?arsId=정류소번호`** |
| **정류소정보조회** | 정류소별 노선 첫차/막차 예정시간 | `?arsId=정류소번호&busRouteId=노선id` |
| **버스도착정보조회** | 정류소노선별도착예정정보목록조회 | **`?stId=정류소ID&busRouteId=노선ID&ord=정류소순번`** ← **arsId 아님** |
| **버스도착정보조회** | 경유노선전체정류소별도착예정정보 | `?busRouteId=노선ID` |
| **노선정보조회** | 노선번호목록조회 | **`?strSrch=노선번호`** ← 노선명으로 검색 |
| **노선정보조회** | 노선경로목록조회 | `?busRouteId=` → **경로를 좌표 리스트로 출력** |
| **버스위치정보조회** | 노선버스위치정보목록조회 | `?busRouteId=노선ID` |

| 확인 항목 | 결과 | 근거 |
|---|---|---|
| arsId를 직접 받는 API가 있는가 | **예 — 정류소정보조회 서비스** | S5 |
| 도착정보조회 서비스도 arsId를 받는가 | **아니오 — `stId`+`busRouteId`+`ord`** | S5 |
| **ARS → stId 변환이 필요한가** | **필요하다** (정류소정보조회 계열로 얻는 경로가 있을 것으로 보이나 응답 미검증) | S5 |
| `ord`(정류소 순번)를 우리가 갖고 있는가 | Graph Core의 `seq`가 후보. **API의 ord와 동일 체계인지 미검증** | — |
| 우리 5자리 stopId와 API arsId 포맷이 동일한가 | **미확인** | — |
| 방향쌍(01009/01010 등)을 독립 정류장으로 구분 가능한가 | **미확인** — 실제 응답으로만 판정 | — |

**가장 단순한 경로 후보**: `고유번호별정류소항목조회 ?arsId=01009` 가 arsId만으로 도착예정정보를
반환한다고 기술돼 있어, Stop 페이지 용도에 stId 변환 없이 바로 쓸 수 있는 가능성이 있다.
다만 **문서 설명만으로 응답 스키마를 확정하지 않는다** — RT-1 실측 대상.

**추정 금지 원칙에 따라 "매칭된다"고 판정하지 않는다.** 구조는 성립, 검증은 RT-1.

## K. Failure UX

**판정: PASS — 안전한 degrade 설계가 가능하다.**

근거: 우리 Stop 페이지는 이미 정적 정보(공식명·ARS·경유 노선·노선별 순서·이전/다음 정류장·
provenance)만으로 6/6 콘텐츠 계약을 충족한다. 실시간은 **추가 블록**이므로, 실패 시 그 블록만
빠져도 페이지의 기존 가치가 유지된다.

| failure state | 대응 가능성 |
|---|---|
| timeout / 5xx / quota exceeded | 실시간 블록 미렌더 + 안내 문구 |
| route·stop 응답 없음 | 동일 |
| stale response | **마지막 값을 "현재"처럼 표시하지 않는다**는 원칙으로 처리 |
| 응답에 차량 정보 없음 | **"현재 제공되는 실시간 정보 없음"** 수준으로만 표시 |

⚠️ **응답 부재로 운행 종료를 추론하지 않는다.** "지금은 운행 시간이 아닙니다" 같은 표현은
API 응답이 비었다는 사실만으로 말할 수 없다 — 차량 미운행·API 장애·데이터 미제공이 모두 같은
빈 응답으로 나타날 수 있기 때문이다. 이는 이 프로젝트가 가장 피해온 **거짓 확정**에 해당한다.
운행 시간 안내는 계속 **정적 운영정보(C2O 계약)** 가 담당하고, 실시간 블록은 자기 상태만 말한다.

금지 유지: 임의 예상값 생성 금지 · 마지막 값 현재 표시 금지 · 응답 부재로 운행 상태 추론 금지 ·
정적 정보는 항상 표시. 정확한 카피는 후속 설계 단계에서 확정한다(이번 라운드에서 확정하지 않음).

## N. 최종 판정: **CONDITIONAL**

문서 조사만으로는 GO를 선언할 수 없다. 그러나 **NO-GO 근거도 발견되지 않았고**,
핵심 구조(공식 API 존재 · arsId 직접 지원 · 상업적 이용 허용 · 자율주행 노선의 실시간
정보 제공 공식 진술)는 성립한다.

### DOCUMENT-ONLY LIMIT (숨기지 않고 명시)

다음 4가지는 **공개 문서만으로는 확정할 수 없다**:

1. OA-1091/OA-1093 응답에 우리 11개 자율주행 노선이 실제로 포함되는가
2. 우리 ARS 5자리 stopId가 API `arsId`와 그대로 매칭되는가
3. 실시간 갱신 주기가 "몇 분 뒤 도착" 표시에 적합한가
4. 야간(22:00~05:00) API 가용성과 호출 한도

이는 조사 실패가 아니라 **문서 조사의 구조적 한계**이며, 정확히 RT-1(키 1개 발급 + 실호출)로
해소되는 항목들이다.

## O. 후속 제안 — Phase RT-1 (별도 승인 필요, 이번 라운드에서 실행 금지)

**RT-1의 목적은 기능 개발이 아니라 N절 UNKNOWN 4칸을 실측으로 닫는 것이다.**

### 확대 추론 금지 (RT-1 절대 규칙)

> **한 정류장·한 노선의 성공을 다른 노선으로 확대 추론하지 않는다.**

`arsId=01009` 호출이 성공하고 응답에 A160이 있더라도 그것으로 확정되는 것은
**"01009에서 A160의 도착정보가 공개 API로 조회된다"** 하나뿐이다. 다음은 확정되지 않는다:

- 나머지 8개 노선의 coverage (노선별 독립 검증 필요)
- 다른 정류장에서의 동작 (Stage 1 7개 각각 검증 필요)
- 방향쌍 독립 분리 (`arsId가 다르니 당연히 분리된다`는 추론 금지 — 실제 응답으로 판정)
- freshness (단발 응답으로 판정 불가 — 간격을 둔 반복 관측 필요)
- 야간 가용성 (주간 성공은 야간을 증명하지 않는다 — 실제 운행 시간대 관측 필요)
- 안정성 (1~2회 성공은 한도·장애 정책의 근거가 아니다)

노선명 문자열이 같다고 동일 노선으로 확정하지 않으며, route master의 실제 `busRouteId`와
기·종점·정류장 순서를 함께 대조해야 한다. 모호하면 **UNKNOWN을 유지**한다.

### 검증 대상 (scope 확정 아님 — 후속 지시서에서 확정)

```
Coverage    11개 노선 각각 독립 판정 (route master · arrival · vehicle 별로)
Matching    Stage 1 7개 stop + 방향쌍 3쌍(01009/01010, 01013/01014, 01007/01008) 독립 호출
Freshness   실제 운행 중인 노선에서 간격을 둔 반복 관측 (고빈도 polling 금지)
Limits      호출 한도·오류 코드·장애 정책 — 가능한 한 문서로 먼저 확보
야간        실제 운행 시간대(03:00~04:00 KST 전후) 관측.
            단 "데이터 없음 = API 장애"로 판정하지 않고 차량 미운행과 분리
Terms       인증키 이용약관 확보 (Terms Gate의 UNKNOWN 축)
```

**RT-1도 구현이 아니다.** 인증키는 사용자가 직접 발급하며, 키를 Git·docs·로그·보고서에
남기지 않는다. 실호출 전 활용가이드 선검토 결과를 먼저 보고하고 사용자 승인을 받는다.
