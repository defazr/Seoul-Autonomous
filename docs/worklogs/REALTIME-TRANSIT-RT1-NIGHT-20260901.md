### 2-1. arrival

3회 관측 내내 `출발대기` 고정. **`term=140`은 정적 SSOT의 `headway=140 min`과 정확히 일치**한다.

### 2-2. freshness — `mkTm` 갱신 확인

```
23:14:50.0  →  23:15:10.0  →  23:15:50.0      (간격 20초, 40초)
```

**응답이 캐시된 고정값이 아니라 실제로 갱신되고 있음이 확인**됐다. 단 `arrmsg`·`term`·`staOrd` 등 내용은 불변이었다.

### 2-3. position — 차량 0대

```
http=200  headerCd=4  「결과가 없습니다」  itemCount=0
```

**우회하지 않았다.** 대안 endpoint(`getBusPosByRouteSt` 등)로 넘어가지 않고 원문을 그대로 기록했다(지시 준수).
차량 0대를 **"미지원"으로 승격하지 않는다.** 23:15는 첫차 23:00 직후이며 배차 140분인 노선이므로,
**차량이 아직 투입되지 않은 상태**로 보는 것이 자연스럽다(A160 세션에서 endpoint 정상 작동이 증명됨 — §4-1).

### 2-4. 이상 필드

```
firstTm = 2026083100     ← 10자리. 공식 문서 규격은 14자리(예: 20230927041000)
lastTm  = 2026083100     ← firstTm 과 동일값
```

**형식이 규격과 다르다.** A160 세션에서는 정상 14자리가 나왔으므로(§3-4) **노선별로 값 품질이 다르다**는 뜻이다.
→ **`firstTm`/`lastTm`을 "다음 운행시각"으로 해석하지 않는다**는 기존 금지를 유지한다.

## 3. 세션 B — 새벽A160 (2026-09-01 화 03:35~03:36) ★ 핵심

### 3-1. position — **실차 좌표 이동 관측** ⭐

차량 1대: `vehId = 100000104` · `plainNo = 임3131` (임시번호판 — 시범 차량 특성과 정합)

| # | gpsY (위도) | gpsX (경도) | dataTm | stopFlag | sectOrd |
|---|---|---|---|---|---|
| 1 | 37.677723 | 127.044977 | 03:34:56 | 1 | 4 |
| 2 | 37.677183 | 127.044798 | 03:35:22 | 0 | 4 |
| 3 | 37.673313 | 127.044163 | 03:35:53 | 1 | 5 |

**실측 이동량**

```
#1→#2    62.1 m / 26초 =  8.6 km/h   (stopFlag 1→0 = 정류소 출발)
#2→#3   433.9 m / 31초 = 50.4 km/h   (stopFlag 0→1 = 다음 정류소 도착, sectOrd 4→5)
합계     496 m / 57초
```

- 좌표는 **WGS84 십진도**이며 서울 도봉구 일대(A160 기점 도봉산역광역환승센터 부근)에 해당한다.
- `sectOrd 4→5`는 정적 SSOT의 4번(서울북부지방법원.검찰청.도봉역성황당) → 5번(신도봉사거리) 구간과 정합적이다.
- **속도·정차 패턴이 실제 버스 운행과 일치**한다(정차 중 저속 → 주행 중 50km/h → 다음 정류소 정차).
- → **`getBusPosByRtid` endpoint 정상 작동, 좌표는 실시간이며 지도 표시가 기술적으로 가능하다.**

### 3-2. freshness — 두 축 교차 확인

```
mkTm   (도착) 03:34:50.0 → 03:35:10.0 → 03:35:55.0    간격 20초, 45초
dataTm (위치) 03:34:56   → 03:35:22   → 03:35:53      간격 26초, 31초
```

**두 축 모두 독립적으로 갱신**된다. 30초 간격 폴링으로 매번 새 값을 얻었다.

> ⚠️ **문서값과 실측값은 분리해 기록한다.**
> 문서상 "5초 갱신" = *GPT가 확인한 업로드 공식 가이드 근거이며 CC 독립 재검증이 아님*.
> **본 관측의 실측 갱신 간격은 20~45초**다. 30초 간격 3회 관측이라 **더 짧은 주기를 배제하지 못한다**
> (폴링 간격이 갱신 주기보다 길면 실제 주기를 과대 추정한다). 즉 실측값은 **"최소 이 정도로는 갱신된다"**는
> 하한선이며, 정확한 주기는 이 데이터로 확정할 수 없다.

### 3-3. arrival — `회차대기` + A741 카운트다운

| 노선 | #1 | #2 | #3 |
|---|---|---|---|
| **새벽A160** | **`회차대기`** | **`회차대기`** | **`회차대기`** |
| 새벽A741 *(참고표시)* | `25분후[6번째 전]` / `출발대기` | `25분후[6번째 전]` / `운행종료` | **`24분후[6번째 전]`** / `운행종료` |
| 심야A21 | `출발대기` | `출발대기` | `출발대기` |

- **A741에서 실제 도착 카운트다운(`25분후` → `24분후`)이 관측**됐다. 판정 근거로 쓰지 않으나,
  **`N분후[K번째 전]` 패턴이 실운행 중 정상 동작함**을 보여주는 관측 사실이다.
- ⚠️ **A160은 차량이 실제로 주행 중인데도 `arrmsg`는 `회차대기`였다.**

  → **`arrmsg`(해당 정류소 기준 도착 상태)와 `position`(차량 실제 위치)은 서로 다른 축이다.**
  이 둘을 같은 것으로 취급하면 안 된다. **제품 설계에 직결되는 발견이다.**

## 4. Gate 판정

### 4-1. A21 position 실패 = route-specific (사전 고정 규칙 적용)

사전에 *"한쪽만 position 성공해도 전체 실패로 보지 않고, route-specific 차이인지 endpoint 문제인지 구분한다"*고
고정했다. 적용 결과:

```
동일 endpoint getBusPosByRtid 로
  A21  (23:15) → 차량 0대, headerCd=4
  A160 (03:35) → 차량 1대, 좌표 정상, 이동 확인
→ endpoint 는 정상. A21 은 그 시각에 차량이 투입되지 않았을 뿐이다.
→ **endpoint 문제 아님. route/시각 특이성으로 판정한다.**
```

### 4-2. Localization — **PASS 금지 유지**

| 시점 | 알려진 arrmsg 패턴 |
|---|---|
| RT-1 1차 (주간) | `N분후[K번째 전]` · `곧 도착` · `운행종료` — 3종 |
| **본 관측** | **+ `출발대기` · `회차대기` — 신규 2종** |
| 현재 | **5종, 그러나 집합이 닫혔다는 근거 없음** |

## 6. RT-2 / RT-3 설계에 직결되는 발견

1. **`arrmsg` 와 `position` 은 다른 축이다** (§3-3). 차량이 주행 중이어도 특정 정류소 기준 `arrmsg` 는
   `회차대기` 일 수 있다. **"몇 분 후"와 "지도 위 점"을 같은 사실의 두 표현으로 다루면 안 된다.**
2. **평상시 화면 문제가 실측으로 확인됐다.** 관측 6회 중 A160·A21이 정상 도착값을 보인 경우는 **0회**다
   (`운행종료`·`출발대기`·`회차대기`뿐). → **RT-2 우선 검토안(운행시간 상시 노출 + 실시간 카드 조건부)이
   실측으로 뒷받침됐다.** 항상 노출형이면 대부분의 시간에 "대기 중" 문구만 보이게 된다.
3. **`출발대기`·`회차대기`는 "운행종료"와 의미가 다르다.** 전자는 곧 운행할 상태이고 후자는 종료다.
   EN 렌더에서 이 구분이 사라지면 사용자가 오판한다.
4. **지도는 기술적으로 가능하다** — 좌표 실측·이동 확인 완료. 단 `dataTm` 기준 **"약 N초 전 위치"** 표기가
   필수다(실측 갱신 간격 20~45초 = 지도 위 점은 항상 과거다).
5. **차량 1대 운행** — A160은 관측 시점에 차량이 1대뿐이었다. 지도에 점 하나가 뜨는 화면이 될 수 있으며,
   이는 "실시간 지도"의 기대치를 관리해야 한다는 뜻이다.

## CC 이견 및 아이디어

### ① 지시서에 대한 이견

없음. 관측 항목·예산·우회 금지·판정 규칙 전부 그대로 수행했다. A21 position 빈 응답에서 **대안 endpoint로
넘어가지 않고 원문만 기록**했으며, 사전 고정한 route-specific 판정 규칙을 적용했다.

### ② 발견한 리스크

- **Freshness 측정 설계에 한계가 있었다.** 30초 간격으로 폴링하면 실제 주기가 5초여도 20~45초로 보인다.
  이번 값은 **"최소 이 정도로는 갱신된다"는 하한선**일 뿐이며, 이를 "갱신 주기 = 20~45초"로 기록하면 틀린다.
  정확한 주기가 필요하면 **5초 간격 짧은 버스트 관측**이 별도로 필요하다(초당 한도 코드 23 주의).
- **`getBustimeByStation` 이 양 세션 모두 실패**했다. 파라미터 조합(`stId`+`busRouteId`) 문제인지,
  이 노선들에 데이터가 없는 것인지 구분되지 않는다. → **"운행종료 → 다음 운행"을 공식값으로 처리하는 경로는
  현재 확보되지 않았다.** 이 후보는 보류 상태로 내려간다.
- **`firstTm` 값 품질이 노선마다 다르다** (A21 10자리 / A160 14자리이나 05:58). 정적 SSOT와 어긋나므로
  이 필드에 의존하는 설계는 위험하다.
- **A21 정류소 수 40(정적) vs 44(API)** 불일치는 이번 관측의 부수 발견이며 원인 미확인이다.

### ③ 더 나은 대안

- **Localization 을 닫으려면 관측 2회로는 부족하다.** 신규 패턴이 계속 나오고 있으므로,
  **여러 시간대·여러 노선의 arrmsg 를 수집하는 저비용 라운드**가 필요하다. 다만 이건 실시간 기능을
  **한국어로만 먼저 출시**하면 우회할 수 있는 문제이기도 하다 — 원문을 그대로 보여주면 패턴 집합을
  닫을 필요가 없다. **EN 구조화 렌더가 진짜 병목**이다.
- **RT-2 를 도착정보로 시작하는 판단이 이번 데이터로 더 강해졌다.** 지도는 좌표가 확인됐지만
  차량 1대·과거 위치·기대치 관리 문제가 있어 난이도가 높다.

### ④ 제품/기술 개선 아이디어

- **`출발대기`/`회차대기`는 오히려 좋은 재료다.** "운행종료"만 있으면 죽은 화면이지만,
  `출발대기`는 **"곧 운행 시작"**이라는 긍정 신호다. 심야A21이 23:15에 `출발대기`였다는 건
  **첫차를 기다리는 사용자에게 의미 있는 정보**다. 단순 필터링으로 버리지 말 것.
- **`term`(배차간격)이 정적 SSOT와 정확히 일치**했다(140분). 이는 API 값을 **정적 데이터 검증에 역으로 쓸 수 있다**는
  뜻이기도 하다. 다만 이번엔 1건 일치일 뿐이므로 일반화하지 않는다.
- **`plainNo = 임3131`(임시번호판)** 은 자율주행 시범 차량 식별에 쓸 수 있는 단서다.
  다만 차량번호 노출은 개인정보·운영정보 성격을 검토해야 하며, 제품에 표시할 이유도 없다. **표시하지 않는 쪽**을 권한다.

### ⑤ 이견 없음 아님

RT-2 설계 전에 포그린이 알아야 할 실질 사항이다.
