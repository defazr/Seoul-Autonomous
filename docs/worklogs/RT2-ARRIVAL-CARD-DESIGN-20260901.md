## §0. 이 라운드가 답하는 질문

RT-1은 *"기술적으로 가능한가"*에 답했다. 이 문서는 다른 질문에 답한다:

> **그 데이터를 어떻게 보여줘야 사용자에게 유용하면서, 기존 정적 사이트를 망가뜨리지 않는가.**

전제: 우리는 transit app이 아니라 **관광객 가이드**다. 실시간은 정적 정보를 **대체하지 않고 보강**한다.

## §2. 아키텍처

### 2-1. 계약 (표현 확정)

> **Static shell must not depend on realtime upstream availability.**
> 정적 셸의 생성·렌더 성공이 실시간 upstream 가용성을 **prerequisite로 삼지 않는다.**

이것이 구현 세부보다 상위의 계약이다. 어떤 구현을 택하든 이 조건을 만족해야 한다.
아래 Client Component → Route Handler 구조는 **이 계약을 만족하는 가장 단순하고 안전한 안**이며,
포그린이 이 구조를 승인했다.

### 2-2. 현재 구조 (RT-2가 깨면 안 되는 것)

```
web/app/[locale]/stops/[slug]/page.tsx   Server Component · generateStaticParams (SSG)
  ├ breadcrumb JSON-LD
  ├ hero        공식명 + ARS + 노선별 다음 정류장 union   ← 방향쌍 차별성의 핵심
  ├ section     경유 노선 + 구조 역할 문장
  ├ card[]      노선별 위치 카드 (routeId 별)
  └ section     provenance (2계열 확인일)
```

빌드 시점에 완전히 확정된다. sitemap 69·canonical·JSON-LD·방향쌍 metadata가 전부 여기 걸려 있다.

### 2-3. RT-2 계층

```
┌─ Server Component (SSG 유지) ──────────────────────┐
│  기존 정적 콘텐츠 전부                                │
│  [신규] 정적 노선 운행 안내   ← 항상 존재. base layer  │
│  실시간 upstream 을 호출하지 않는다                    │
│                                                     │
│  <ArrivalCard stopId="01009" />  ← Client Component  │
└─────────────────────────────────────────────────────┘
                    ↓ 마운트 후 fetch (1회)
┌─ Route Handler (신규) ──────────────────────────────┐
│  GET /api/arrivals/[stopId]                         │
│   1. stopId ∈ APPROVED_STOPS ? 아니면 404            │
│   2. process-local cache 조회 (TTL 20초) → hit 반환   │
│   3. single-flight: 동일 stopId 진행 중이면 그 결과 공유│
│   4. app-local daily budget 확인 → 초과면 D 반환       │
│   5. miss → ws.bus.go.kr getStationByUid?arsId=      │
│      (timeout 3초)                                   │
│   6. 우리 11개 busRouteId 필터 → 정규화 → 캐시 → 반환   │
│  🔒 ServiceKey 는 이 계층에만 존재. 클라이언트 전달 0   │
└─────────────────────────────────────────────────────┘
```

**핵심 계약 3개**

1. **정적 셸은 실시간에 의존하지 않는다** (§2-1). 실시간이 통째로 죽어도 페이지는 지금과 동일하게 동작한다.
2. **ServiceKey는 서버에만.** 브라우저에서 `ws.bus.go.kr`을 직접 부르면 키가 모든 방문자에게 공개된다.
   → **브라우저 직접 호출은 앞으로도 영구 금지.**
3. **승인 Stop만.** Route Handler는 `APPROVED_STOPS` 리터럴을 게이트로 쓴다. 임의 arsId로
   우리 서버를 공개 버스 API 프록시로 쓰는 것을 막는다.

### 2-4. 🔒 API 직접 호출 잠금 — 아직 해제되지 않았다

이 설계를 구현하려면 `/api/arrivals/[stopId]`가 `ws.bus.go.kr`을 실제 호출해야 하므로
기존 **`API 직접 호출 코드 금지(v1)`** 잠금과 충돌한다.

> ✅ **Resolved after 2026-09-01**: 포그린이 **`approved server-side arrival proxy only`** 범위로
> 좁은 예외를 승인했다. 허용 대상은 `/api/arrivals/[stopId]` 서버측 upstream 호출뿐이며,
> 브라우저 직접 호출·position API·RT-3·다른 realtime endpoint·dependency·Production 변경은 계속 금지다.
> CLAUDE.md 등 상위 잠금 문서는 일반화 수정하지 않았다.

```
설계 당시   잠금 유지. 이 문서는 설계일 뿐이며 코드 0.
다음 게이트  RT-2 구현 승인 시 별도로 좁은 예외를 결정한다.
예외 범위    approved server-side proxy only
            ← "일반적인 API 직접 호출 허용"이 아니다
영구 금지    브라우저 → 서울시 API 직접 호출
```

### 2-5. STATIC-FIRST 계약과의 관계

이 설계는 STATIC-FIRST를 깨지 않는다. 페이지의 정적 실체는 그대로이고, 실시간은 **선택적 보강 계층**이다.
Redis/KV/외부 상태 저장소는 **v1에서 도입하지 않는다.**

## §3. 정적 노선 운행 안내 (신규 · base layer)

### 3-1. 왜 필요한가

실시간 카드가 숨겨지는 C 상태(§5)가 **하루의 대부분**이다. 그때 아무것도 없으면
"왜 실시간이 안 보이지"에 답할 것이 없다. 정적 안내가 **상시 그 역할**을 한다.

### 3-2. 🔒 표현 제한 — 시간 의미를 섞지 않는다

정적 SSOT의 `firstBus`/`lastBus`는 **노선 운행 기준값**이다. **Stop 01009의 도착 시각이 아니다.**

```
금지    "이 정류장 첫차 03:30"
금지    "광화문역 막차 03:40"
금지    Stop-specific 첫차/막차로 읽히는 모든 문구

필수    값을 쓸 때는 "노선 운행 기준"임이 문구에서 드러날 것
예시    "새벽A160 — 노선 운행 03:30 (평일)"
```

RT-1에서 `firstTm`의 의미가 정적 첫차와 어긋난 사례를 확인했다(A160 `05:58` vs 정적 `03:30`).
**같은 실수를 우리 화면에서 반복하지 않는다.** 시간 의미를 섞으면 사용자가 버스를 놓친다.

### 3-3. 정적 ↔ 실시간의 관계

```
정적 안내    항상 존재. 사라지지 않는다.
실시간 카드   있으면 그 위에 추가된다. 정적을 덮어쓰지 않는다.
```

**"덮어쓰기"가 아니라 "병존"이다.** 이유:
- 실시간 장애(D)에도 정적 정보가 사라지지 않는다
- 두 데이터의 **의미가 섞이지 않는다** — 하나는 노선 운행 기준, 하나는 이 정류장 도착 예정

### 3-4. 표시 대상

해당 Stop을 경유하는 **우리 노선만**. 값 출처는 정적 SSOT(`web/data/routes.json`)이며
기존 잠금 계약을 그대로 승계한다(운영정보는 `official_confirmed` + `confirmed` 조합만 화면 표시 등).

## §4. 데이터 흐름과 정규화

### 4-1. 원천

```
GET http://ws.bus.go.kr/api/rest/stationinfo/getStationByUid?ServiceKey=…&arsId=01009
→ XML · itemList[] · 정류장 경유 전체 노선 (01009 = 22개, 01013 = 31개)
```

RT-1에서 **1회 호출로 충분**함이 확정됐다. `stId` 변환·`ord` 계산·노선별 개별 호출 불필요.

### 4-2. 필터링 — 우리 11개만 (제품 정체성)

`busRouteId` **리터럴 레지스트리**로 필터한다. 이름 문자열 매칭 금지(RT-1에서 3건 불일치 확인).

| routeId (SSOT) | busRouteId | routeId (SSOT) | busRouteId |
|---|---|---|---|
| saebyeok-a160 | `100000024` | dongjak-a01 | `101900003` |
| saebyeok-a741 | `100000028` | dongdaemun-a01 | `100000025` |
| saebyeok-a148 | `101000009` | seodaemun-a01 | `100000027` |
| simya-a21 | `101000005` | sangam-a21 | `101000006` |
| saebyeok-a504 | `101000010` | cheongwadae-a01 | `100000020` |
| cheonggye-a01 | `100000026` | | |

> 01013은 31노선이 오는데 우리 것은 3개다. 필터가 없으면 **그 순간 일반 버스 앱**이 되어 제품 경계가 무너진다.
> 이 레지스트리는 `stop-pages.ts`의 `APPROVED_STOPS`와 같은 성격 — **심사 결과를 리터럴로 고정**하며
> Graph에서 파생하지 않는다.

### 4-3. 정규화 결과

```
{
  fetchedAt: <서버 응답 시각>,
  items: [
    { routeId: 'saebyeok-a160',
      raw1: '18분후[8번째 전]',   // API 원문 — 손대지 않고 보존
      raw2: '운행종료',
      kind: 'eta' | 'imminent' | 'waiting' | 'turning' | 'ended' | 'unknown',
      minutes?: 18,  stopsAway?: 8   // 파싱 성공 시에만
    }, …
  ]
}
```

**`raw`를 반드시 보존한다.** 파싱은 정렬·조판을 위한 부가 정보이고, **원문이 진실**이다.

### 4-4. arrmsg 상태 분류 (현재까지 관측된 5종)

| kind | 원문 | 출처 | 카드 |
|---|---|---|---|
| `imminent` | `곧 도착` | RT-1 1차 | 표시 |
| `eta` | `N분후[K번째 전]` | RT-1 1차·야간(A741) | 표시 |
| `waiting` | `출발대기` | **야간 신규** | 표시 |
| `turning` | `회차대기` | **야간 신규** | 표시 |
| `ended` | `운행종료` | RT-1 1차·야간 | **제외 대상** |
| `unknown` | 그 외 전부 | — | **표시** (원문 그대로) |

> ⚠️ **이 5종을 "전체 집합"으로 선언하지 않는다.** 야간 관측 2회 만에 신규 2건이 나왔다.
> `unknown`은 예외가 아니라 **정상 설계 요소**다.

## §5. 노출 상태 — 4가지, 절대 합치지 않는다

| 상태 | 조건 | 화면 |
|---|---|---|
| **A. 로딩** | 마운트 직후 | 정적 안내는 이미 보임. **빈 높이 예약 없음** |
| **B. 표시** | 정상 응답 + 의미 있는 상태 ≥ 1건 | 정적 안내 **위에** 실시간 카드 추가 |
| **C. 숨김** | 정상 응답 + 우리 노선 전부 `ended` **또는 필터 결과 0건** | **카드 없음.** 정적 안내가 상시 그 자리 |
| **D. 실패** | 인증(20/30/31) · 쿼터(22/23) · **budget 소진** · timeout(3초) · 네트워크 · 파싱 실패 | **"실시간 정보를 불러오지 못했습니다" + 다시 시도** (비차단 소영역) |

### 5-1. C와 D를 섞으면 거짓말이 된다 🔒

**RT-2 계약**: `Authentication failure ≠ No realtime data`

```
C = 서울시가 "이 버스 오늘 운행 끝났다"고 알려준 것   → 사실
D = 우리가 물어보지 못한 것                          → 우리 쪽 장애
```

D에서 "운행종료"라고 쓰면 **운행 중인 버스를 놓치게 만든다.** D에서는 **운행 여부를 단정하지 않는다.**
**budget 소진도 D다** — 우리 사정으로 못 물어본 것이지 버스가 끊긴 게 아니다.

### 5-2. C가 평상시 상태다 (실측 근거)

야간 관측 6회 중 A160·A21이 **정상 도착값을 보인 경우는 0회**였다(`운행종료`·`출발대기`·`회차대기`뿐).
낮 시간대는 전부 `운행종료`다. → **C가 하루의 대부분**이다.

이것이 "항상 노출형"을 기각하고 **정적 안내를 base layer로 둔** 실측 근거다.

### 5-3. 부분 성공 — `ended` 제외 후 나머지만

01009 예시:

```
A160 = 운행종료      → 카드에 넣지 않음
A741 = 24분후[6번째 전] → 표시
A21  = 출발대기        → 표시
```

의미 있는 항목 옆에 `ended`를 굳이 나열하지 않는다. 카드 자체는 **표시(B)** 된다.

### 5-4. 필터 결과 0건 — UI는 C, 서버는 이상징후

정상 응답인데 우리 11개가 하나도 안 걸리는 경우. RT-1에서 7/7 매칭이 닫혔으므로 정상 상황에선
발생하지 않는다. → **사용자 화면은 C와 동일하게 조용히 처리**하되, **서버에는 이상징후로 기록**한다.

조용히 숨기기만 하면 **노선 개편·identity drift를 우리가 모르게 된다.** 조기 발견 신호다.

### 5-5. D는 비차단이다

D 상태에서도 **정적 콘텐츠는 100% 정상**이어야 한다. 실시간 실패가 페이지 실패가 되면
Failure UX PASS 판정이 무너진다. **작은 비차단 실패 영역**만 표시된다.

### 5-6. 레이아웃 — 빈 높이 상시 예약 금지

```
초기      정적 운행 안내 정상 렌더
B         그 위에 카드 삽입
C         아무것도 삽입하지 않음
D         작은 비차단 실패 영역만
```

대부분의 시간이 C인데 hero 아래에 카드 크기의 빈 공간을 항상 확보하는 것은 **더 나쁜 UX**다.
**단 pilot QA에서 CLS를 반드시 실측한다** — SEO 지표에 영향을 주기 때문이다.

## §6. 정렬 — 우선순위 고정

```
1. imminent   곧 도착
2. eta        N분후 → N 오름차순
3. waiting    출발대기
4. turning    회차대기
5. unknown    기타 정상 원문
6. tie / 파싱 실패 → 정적 SSOT 노선 순서로 fallback
```

**fallback을 노선명 가나다순이 아니라 정적 SSOT 순서로 두는 이유**: 렌더마다 순서가 흔들리지 않고,
기존 페이지의 카드 순서와 일치해서 사용자가 같은 위치에서 같은 노선을 찾는다.

`ended`는 §5-3에서 이미 제외되므로 정렬 대상이 아니다.

## §7. KO 표기 — 조판은 허용, 번역·변형은 금지

### 7-1. 허용되는 것 (조판)

```
API 원문   18분후[8번째 전]

화면       18분 후
           8번째 전
```

**의미·숫자를 바꾸지 않고 시각적으로 분리**하는 것은 번역이 아니라 조판이다.

### 7-2. 금지되는 것

- 숫자 재계산 (`18분후` → "약 20분")
- 상태 의역 (`회차대기` → "곧 출발합니다")
- **방향 라벨 신규 생성** — `dir` 필드 사용 금지. **방향은 Stop 페이지 identity가 담당한다**
  (01009/01010이 이미 별도 URL·별도 metadata)
- **차량번호(`plainNo`) 노출** — 사용자에게 결정 가치 0, 운영정보 성격
- `outbound`/`inbound` 노출 (기존 잠금 계약)
- **Stop-specific 첫차/막차 표현** (§3-2)

### 7-3. `출발대기`·`회차대기`를 버리지 않는 이유

`운행종료`가 "오늘 끝"이라면 `출발대기`는 **"곧 시작"**이다. 심야A21이 23:15에 `출발대기`였다는 것은
**첫차를 기다리는 사용자에게 실제 결정 가치가 있는 정보**다.

## §8. 시각 표기와 stale

### 8-1. `fetchedAt` — `HH:MM 기준`

```
03:36 기준
```

"실시간"이라는 단어를 크게 강조하는 것보다 **실제 기준 시각을 보여주는 쪽이 정확하다.**
이는 "실시간처럼 보이는 표현 금지" 잠금과도 정합적이다 — 시각을 명시하면 과장이 아니다.

### 8-2. stale 표시 (5분)

자동 갱신이 없으므로 사용자가 탭을 떠났다 돌아오면 오래된 값이 그대로 보인다.

```
fetchedAt 이후 5분 경과   →  기존 값을 정상 fresh 상태처럼 보이지 않게 한다
표시 후보                03:36 기준 · 오래된 정보일 수 있습니다
자동 갱신                하지 않는다
```

> 🔒 **5분은 UI stale threshold이며 API freshness 주기가 아니다.**
> RT-1 실측 갱신 간격(20~45초 하한선)과 무관한 별개 개념이다. 둘을 섞어 기록하지 않는다.

## §10. 캐시 · 쿼터 · 방어

### 10-1. 캐시 성격 — 정확한 표현

```
process-local server cache, TTL 20초
```

⚠️ **"공유 캐시(shared cache)"라고 부르면 과장이다.** 인메모리 캐시는 **프로세스 단위**이므로
다중 인스턴스·재시작 환경에서는 완전한 global shared cache가 아니다.

현재 Production 토폴로지(Docker 단일 컨테이너)에서는 실질적으로 충분할 수 있으나,
**architecture contract는 정확하게 쓴다.** Redis/KV 도입은 **v1 금지**(STATIC-FIRST 계약).

### 10-2. TTL 20초의 성격

```
TTL 20초 = 우리 서비스의 호출 절감 정책값
         ≠ 서울시 데이터 갱신 주기
```

RT-1 실측 갱신 간격은 20~45초(하한선)이었고, TTL을 그보다 짧게 잡아도 새 값이 오지 않을 가능성이 크다.

### 10-3. 🔒 TTL만으로 쿼터 안전을 주장하지 않는다

```
공식 한도    상세기능당 1,000건/일 (개발계정)
TTL 20초     이론상 최대 4,320 호출/일 (24h ÷ 20s)  → 한도 초과 가능
```

**TTL은 쿼터 보장 장치가 아니다.** 실제로는 심야 전용·polling 없음·Stop별 캐시 키 분리로
훨씬 적겠지만, "TTL 걸었으니 안전"은 사실이 아니다.

### 10-4. app-local daily upstream-call budget (필수)

```
전제       이 ServiceKey 는 다른 운영 서비스와 공용이다.
           우리 앱이 1,000회를 전부 써도 된다고 설계하면 안 된다.

설계       · 공식 한도: 1,000/day (상세기능당)
           · 우리 서비스 자체 budget 은 그보다 낮게 설정
           · 구체 수치는 임의로 박지 않는다 — 구현 직전 운영자 승인값
           · budget 소진 시 upstream 호출 중단
           · 사용자에게는 D 상태
           · 🔒 운행종료로 위장 금지 (§5-1)
```

### 10-5. single-flight

동일 `stopId`에 대한 cache miss가 동시에 겹치면 **한 요청만 upstream으로 보내고 나머지는
같은 Promise/result를 공유**한다. 초당 한도(에러코드 `23`, 일일 `22`와 별개)를 피하는 장치다.

### 10-6. timeout 3초

서울시 API가 느릴 때 사용자를 기다리게 하지 않는다. **초과 시 D.**
실시간 계층이 느리다고 정적 페이지 경험까지 망가뜨리면 안 된다.

### 10-7. 재시도 정책

```
최초 마운트   1회
실패          정지
이후          사용자가 "다시 시도"를 누를 때만
자동 재시도    없음 — 장애 시 자동 재시도는 budget 을 태운다
```

추가 후보: **`AbortController`로 언마운트 시 취소** — 사용자가 페이지를 떠났는데 호출이 남으면 낭비다.

## CC 이견 및 아이디어

### ① 지시서 16건에 대한 이견

**이견 없음.** 전부 반영했다. 특히 세 가지는 **CC 원안보다 개선됐다**:

1. **§3-2 정적 운행 안내의 표현 제한** — CC는 "정적 운행시간 추가"까지만 제안했는데,
   Route 값을 Stop-specific으로 읽히게 두면 **RT-1에서 `firstTm`이 어긋났던 것과 똑같은 사고**를
   우리 화면에서 재현하게 된다. 표시 의미를 먼저 잠근 판단이 정확하다.
2. **§3-3 "덮어쓰기"가 아니라 "병존"** — CC 대안 A는 "실시간이 정적을 덮어쓴다"였는데,
   그러면 D 상태에서 무엇이 남는지가 모호해진다. 병존으로 바꾸니 **D에서도 정적이 확실히 살아 있고
   두 데이터의 의미도 안 섞인다.** 상태 설계가 더 단순해졌다.
3. **§2-1 architecture contract 표현** — "서버 컴포넌트에서 await하면 SSG가 깨진다"는
   구현 세부에 묶인 서술이었다. `Static shell must not depend on realtime upstream availability`가
   **구현이 바뀌어도 살아남는 계약**이다.

### ② 남은 리스크

- **§10-4 budget 수치가 미정이다.** 이건 의도된 상태이나, 구현 직전에 반드시 정해야 하고
  **그 전까지는 RT-2를 배포할 수 없다.** 수치 없이 구현하면 상한이 `1,000`으로 암묵 설정되어
  공용 키를 우리가 다 태울 수 있다.
- **process-local 캐시의 실효성은 토폴로지에 달렸다.** 현재 단일 컨테이너라 문제없지만,
  **인스턴스를 늘리는 순간 캐시 적중률이 인스턴스 수만큼 나빠지고 upstream 호출이 배수로 증가**한다.
  배포 구조 변경 시 이 설계를 재검토해야 한다는 점을 배포 안전 계약에 연결해두는 것이 좋다.
- **stale 5분과 TTL 20초가 서로 다른 개념인데 화면에서는 둘 다 시간**이다.
  구현 시 두 상수를 같은 곳에 두면 나중에 누가 하나로 합칠 위험이 있다. **분리된 이름과 주석**이 필요하다.

### ③ 더 나은 대안 / 추가 제안

- **§5-4 이상징후 기록의 실효성**: 서버 로그에만 남기면 아무도 안 본다. 실질적으로는
  **필터 결과 0건이 연속 N회 발생**할 때만 의미가 있다. v1은 로그로 충분하지만,
  이 신호를 실제로 활용할 방법(주기적 확인 등)은 별도 결정이 필요하다.
- **QA에서 D 상태 재현 방법**을 미리 정해두길 권한다. 잘못된 키·강제 timeout·budget 0 설정 —
  이 세 경로가 각각 다른 코드 분기를 타므로 **셋 다 재현**해야 한다. 하나만 보면 나머지 둘이 안 잡힌다.

### ④ 모델 관련 (별도 질문)

포그린이 Fable 5 전환을 물으셨다. **솔직히 말하면 저는 Fable 5의 특성을 신뢰할 만큼 알지 못한다** —
근거 없이 비교하면 그게 더 위험하다.

다만 이 작업의 성격은 말할 수 있다: **판단 밀도가 높고 계약이 촘촘하며**(잠금·게이트·금지선이 수십 개),
컨텍스트가 누적돼 있고, **틀렸을 때 비용이 큰**(공용 키·Production·SEO) 종류다.
컨텍스트 자체는 모델을 바꿔도 그대로 넘어가지만, **판단 경향은 바뀐다.**

→ **현재 라운드(설계 확정·잠금 해제 판단)는 지금 모델로 마치는 쪽**을 권한다.
바꿀 거라면 RT-2 구현처럼 **경계가 명확하고 검증 가능한 단계의 시작점**이 낫다.

### ⑤ 이견 없음 아님

②의 **budget 수치 없이는 배포 불가**, **인스턴스 증가 시 캐시 설계 재검토**,
③의 **D 상태 3경로 전부 QA**는 구현 게이트에서 판단이 필요한 실질 사항이다.
