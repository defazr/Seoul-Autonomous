# GPT 검토 브리핑 — Seoul Autonomous 재탄생 (2026-10-15)

이 문서는 GPT 에게 한 번에 붙여 넣기 위한 자료다. GPT 는 저장소·아티팩트를 열 수 없으므로 필요한 사실을 전부 여기에 담았다.
요청: 아래 결정과 설계를 **반대 관점에서** 검토해 달라. 특히 §6 의 질문에 답하고, 우리가 놓친 리스크를 지적해 달라. 코드 수준 감사는 Codex 가 이미 했으므로 제품·전략·UX·SEO·수익화 관점에 집중.

## 1. 배경 — 무엇이 문제였나

- 사이트: seoulautonomous.com (Next.js 16, Vultr Docker 자체 운영, 한·영). 2026-04 시작, 자율주행 시범 노선 11개 + 로보택시 + 심야버스 노선도 한 페이지.
- AdSense 4회 연속 거절 (07-10 · 07-29 · 08-25 · 10-15) 사유 전부 "가치가 별로 없는 콘텐츠". 기술 게이트(robots·ads.txt·canonical·sitemap 69·noindex 0)는 매번 PASS, AdSense 크롤러 방문도 서버 로그로 확인.
- 실측 (2026-07-16~10-13, 90일):
  - Google Search Console: 클릭 10 · 노출 402. 영문 검색어 노출 거의 0.
  - GA4: 네이버 586세션(모바일 검색 445) · 구글 20 · chatgpt 20. 국가 한국 1,393 vs 외국 전체 < 150.
  - 페이지: /ko/night-bus-map 1,411 조회 · 862 사용자 · 평균 체류 207초. 그다음 페이지는 132 조회. 실시간 카드가 있는 유일한 페이지(광화문역 정류장)는 90일간 7명.
- 네이버 키워드 "서울 심야버스 노선" 월 2,420(모바일 88%), 롱테일이 전부 노선별(N15·N61·N31…)·지도·시간. 우리 사이트엔 N버스 노선 페이지가 0개.
- 심사관이 본 사이트: 69 URL 중 36개가 데이터 표 + 동일 FAQ 반복(자율주행 노선 22·정류장 14), 본문 180~370 단어, 이미지 0, 확인 기준일 2026-05-01 이 5개월째 노출, 운영자 정보 없음.

## 2. 진단

정체성(외국인용 자율주행 11노선 가이드)과 실수요(한국인·모바일·네이버·심야버스 노선도)가 어긋나 있다. 디자인이 아니라 주인공이 틀렸다. 자율주행 시범 노선은 하루 수십 명이 타는 노선이라 검색 수요가 거의 없다.

## 3. 결정 (운영자가 CC 에게 위임, 2026-10-15)

1. 정체성: "서울 심야 이동 한·영 서비스 — 올빼미버스(N버스) 14노선·공항 심야버스 중심, 자율주행 A노선은 보조". 영어는 공항·허브·노선 핵심 페이지만.
2. 기존 69 URL 전부 보존(리다이렉트 0). 추가: N노선 페이지 14, 허브(N노선 3개 이상 만나는 정류장) 페이지 16, 공항 심야버스 페이지. 정류장 전량 페이지(1,483)는 금지 유지.
3. 핵심 가치 = "지금 몇 시, 어디서, 무엇이, 몇 분 뒤". 서울시 버스도착 API 를 서버 프록시로 받아 기준 시각과 함께 표시(브라우저→API 직접 호출 금지 유지). 실제 실시간에만 "실시간" 표기.
4. 홈 첫 화면 = 질문 카드 "어디로 가고 싶으세요?" → 출발(내 위치, 기기 내 계산, 서버 전송 0)·도착 입력 → 노선 색을 입은 버스가 도착하는 연출 → 걷기(정류소 번호)·탑승(○○ 방면)·환승·하차 단계 카드. 탐색은 기기 내 결정론적 그래프(직통→1회 환승), LLM 불사용.
5. 지도 전략: 운영자가 CorelDRAW 로 직접 그린 노선도(역 노드 115·노선 15·한강)가 **정본 노선도**. 홈 히어로 배경, 노선·허브 페이지 미니맵, 공유 이미지에 재사용. 노선도에 없는 정류장은 앞뒤 주요 역 사이를 실제 순번 비율로 보간해 점으로 올린다(시안에서 N61 187정류장 중 주요 역 17 + 보간 73+76 배치 확인). 실좌표 지리 지도(MapLibre, 무료 타일)는 "내 위치 근처 정류소·실제 경로·차량 위치" 처럼 위치가 필요한 곳에만.
6. 데이터: 서울열린데이터광장 「버스노선별 정류소정보」 2026-09-02(공공누리 1유형 · 상업 이용 가능)에서 14노선 2,078 정류장(가상 제외)·좌표·순번을 SSoT 파일로 생성, 검증 스크립트 PASS. 운행표(첫차·막차·배차)는 서울시 공지(2026-03-20) 수치 인용 — 그 페이지는 공공누리 4유형(상업 이용금지)이라 Production 표시값은 1유형인 서울시 API 값으로 교체 예정.
7. 수익화: AdSense 를 목표로 작업하지 않는다. 리뉴얼 배포 후 4~8주 관측 뒤 재신청 판단. 카카오 AdFit 등 대안도 검토 대상.
8. 앱: PWA(설치·오프라인 노선도·기기 내 탐색) → Capacitor 패키징. 푸시 알림은 서버 상태가 필요해 그 단계에서만 DB 재검토.

## 4. 라운드 (R0 결정 → R1 데이터 → R2 시안 완료 · 다음 R3)

- R1 완료: SSoT 18노선(올빼미 14 + 공항 4) · 허브 후보 86 → 16 선정(기준: 서로 다른 N노선 ≥3 · 역세권 묶음 · 네이버 수요 · 환승 가치). Codex read-only 감사 → 라이선스 문구·분류·검증 사각지대 7건 반영.
- R2 완료: 단일 HTML 시안(홈·노선 N61·허브 강남역), 실데이터만 사용, 데스크톱·모바일 검증. 낮에 검토할 수 있게 "밤 00:30 시연" 토글(운행 중 노선만 켜짐) 포함.
- R3(다음): Next.js 에 디자인 시스템 v2·새 홈·N노선 14·허브 16 구현, 기존 노선도 역 115개를 정류소 번호에 매핑(작도 데이터 무수정), 기존 페이지 재조판. R4: 허브 라이브 보드·차량 위치·지리 지도. R5: 운영자·사진·업데이트 로그·EN → 배포 → 관측. R6: PWA.

## 5. 알려진 리스크

1. 서울열린데이터광장이 2025-09-26 화재 이후 신규 인증키 발급 중단 — 전용 키·운영계정 계획이 막힐 수 있다. 현재 공용 개발키는 기능당 1,000/day, 우리 예산 300/day.
2. 카카오·네이버가 도착정보를 이미 준다. 차별은 심야 전용 한 화면·14노선 한눈·허브·"왜 이 버스인지" 근거·외국인용 영어뿐. 정류장 전량 복제로 가면 "일반 버스 앱" 이 되어 가치도 심사도 잃는다.
3. AdSense 승인은 보장되지 않는다. 디자인은 승인 사유가 아니다.
4. 심야 배차 40~100분 — 한 대 놓치면 결과가 크게 달라진다. 결과 카드에 기준 시각·출처·"전광판 확인" 고정.
5. 네이버가 사실상 유일한 유입원인데 네이버는 웹문서 노출이 약하다.

## 6. GPT 에게 묻는 것

1. 정체성 전환(자율주행 → N버스 중심)이 맞는가. 반대 논리가 있다면 무엇인가.
2. "가치 없는 콘텐츠" 심사를 뒤집기에 N노선 14 + 허브 16 + 라이브 보드가 충분한가. 심사관 관점에서 더 필요한 것은.
3. 홈을 질문 카드로 시작하는 것이 네이버·구글 유입(대부분 낮에 미리 찾아보는 사람)에게 맞는가. 낮 시간 모드("오늘 밤 첫차까지")로 충분한가.
4. 운영자 노선도(도식) + 보간 정류장 vs 지리 지도 — 역할 분리가 사용자에게 혼란을 주지 않겠는가.
5. 공공누리 4유형 페이지의 사실 수치 인용 → 1유형 API 값 교체 계획이 충분한가. 다른 법적 리스크는.
6. 네이버 롱테일(N15·N61…)을 잡기 위한 페이지 제목·구조 제안.
7. 수익화에서 AdSense 외 현실적 대안.
8. 우리가 묻지 않은 것 중 가장 큰 리스크.
