  CC는 값을 **출력하지도 확인하지도 않았다.**
- 🔒 제품화 시 키는 **서버 사이드 전용**. 브라우저 JS 직접 호출 금지 —

## 7. RT-2 후보 (지금 구현 금지)

**계약 승격 1건**

- **`Authentication failure ≠ No realtime data`**
  인증 오류(코드 20/30/31) · 쿼터 초과(22/23) · API 장애를 **"현재 도착정보 없음"이라는 정상 데이터 부재와
  절대 같은 상태로 처리하지 않는다.** 전자는 우리 쪽 장애, 후자는 정상 상태다.

**Architecture consideration (계약으로 승격하지 않음)**

- endpoint 변경 가능성 — 서울시 버스 API는 기관 자체 서버(`ws.bus.go.kr`) 서비스이며,
  포털의 "분산형 → 중앙 개선형 전환" 사업 맥락이 존재한다. **정황일 뿐 확정이 아니다.**
  "주소 하드코딩 금지 확정"으로 올리지 않는다.
- **서비스별 parser 분리** — 도착=XML 전용, 정류소·위치=JSON+XML.
- **identity registry** — busRouteId 11 + stId 7을 `stop-pages.ts`의 `APPROVED_STOPS`처럼 승인 리터럴로 두는 안.
  **아이디어로만 보존, 구현 금지.**

**용량(쿼터) 대응 후보**

1. 상세기능당 1,000건/일 — 캐시 없이 페이지뷰마다 호출하면 **1,000 PV에서 소진**
2. **서버 프록시 + 짧은 TTL 캐시(20~30초)** 가 사실상 필수 후보
3. 운영계정 전환으로 증설 가능(공식 숫자 없음 → 신청해야 확인)
4. 초과 시에도 **실시간 블록만 제거하고 정적 6/6 유지** → 사이트는 죽지 않음
5. 응답에는 우리가 쓰지 않는 노선까지 전부 온다(01013 = 31노선). Stop 페이지는 **우리 11개만 필터링**해야 하며,
   전체 노출은 "일반 버스 앱"이 되어 제품 정체성과 충돌한다.

### ① 지시서에 대한 이견

### ② 발견한 리스크

- **인증 확인은 시점 스냅샷이다.** 마이페이지 승인 확인(08-28)과 실호출(08-29) 사이는 하루였지만,
  야간 게이트가 8/31~9/1이면 **2~3일 간격**이 생긴다. 그 사이 활용정보 상태가 바뀌면 인증 오류가 날 수 있고,
  이를 "노선 미지원"으로 오독하면 안 된다. → 야간 스크립트도 **오류 코드를 원문 그대로 기록**하는 구조를 유지한다.
- **초당 한도(코드 23)** 가 일일 한도와 별개이므로, 야간 반복 관측을 짧은 간격으로 돌리면
  하루 예산이 남아 있어도 차단될 수 있다. 반복 간격은 최소 수 초 이상으로 잡아야 한다.
- **운영계정 트래픽에 공식 숫자가 없다.** RT-2 용량 설계는 실제 신청·승인 실적 없이는 확정 불가다.
- **`getBustimeByStationList`는 노선id가 필수**다(정류소고유번호 + 노선id). 우리는 busRouteId 11개를
  이미 확보했으므로 호출 자체는 가능하지만, **응답의 날짜 의미를 확인하기 전에는 "다음 운행"으로 해석하지 않는다.**

### ③ 더 나은 대안

- 야간 관측에서 **`mkTm`(도착) + `dataTm`(위치) 교차 관측**을 권고한다. 위치 API가 야간에 응답하지 않아도
  도착 쪽에서 갱신성을 판정할 수 있어, 한 번의 창에서 Freshness가 미결로 남을 위험이 줄어든다.
- 야간 관측 대상 Stop은 **01009 하나로 충분**하다. 이번에 7/7 매칭이 닫혔으므로 야간에는 Stop을 넓힐 필요가 없고,
  같은 지점을 **반복 관측**하는 것이 Freshness 판정에 더 유효하다. 호출 예산도 절약된다.
